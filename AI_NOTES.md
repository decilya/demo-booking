## 2. Случаи, где ИИ ошибся (и как заметил)

### Кейс 1. Уникальный индекс вместо `EXCLUDE` для интервалов

**Что предложил ИИ:** «Защитить от пересечений можно уникальным индексом на
`(room_id, starts_at, ends_at)`».

**Почему неверно:** уникальный индекс работает для **точного совпадения**
значений. Для **пересечения диапазонов** (`[t1, t2) ∩ [t3, t4) ≠ ∅`) он
бесполезен: `10:00–11:00` и `10:30–11:30` — разные значения полей, но
пересекаются. В PostgreSQL для этого существует **только** `EXCLUDE USING gist`.

**Как заметил:** при чтении документации PostgreSQL по exclusion constraints
и проверке семантики `tstzrange` с оператором `&&`.

**Исправление:** `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at) WITH &&)` + `btree_gist`.

### Кейс 2. `$start->hour` без конвертации в TZ офиса

**Что предложил ИИ:** «Проверять рабочее время через `$start->hour < 9 || $start->hour >= 20`».

**Почему неверно:** `Carbon::parse("2026-11-10T10:00:00+07:00")->hour` вернёт
`10` (час в оффсете `+07:00`), а не в TZ офиса комнаты. Для московской комнаты
это `06:00 МСК` — нерабочее время, но проверка проходит. Баг воспроизведён
через `curl`: `201 Created` вместо `422`.

**Как заметил:** при планировании тестов на оба TZ — понял, что проверка
`hour` без `setTimezone($office->timezone)` даёт ложные результаты.

**Исправление:** `Carbon::parse(...)->setTimezone($room->office->timezone)`
+ проверка **всего интервала** `[start, end]` в `[09:00, 20:00)`, а не только
часа начала.

### Кейс 3. `btree_gist` не упомянут в миграции

**Что предложил ИИ:** `EXCLUDE USING gist (room_id WITH =, tstzrange(...) WITH &&)`
без `CREATE EXTENSION btree_gist`.

**Почему неверно:** для `room_id WITH =` (integer) PostgreSQL требует
операторного класса из `btree_gist`. Без расширения миграция падает с
`data type integer has no default operator class for access method "gist"`.

**Как заметил:** при первом прогоне миграции на чистой БД.

**Исправление:** `CREATE EXTENSION IF NOT EXISTS btree_gist` в первой строке
`up()`.

### Кейс 4. `QueryException::getCode()` для SQLSTATE

**Что предложил ИИ:** `if ($e->getCode() === '23P01')`.

**Почему неверно:** для PDO `getCode()` в некоторых драйверах возвращает
`HY000` (generic) вместо SQLSTATE. Надёжнее — `$e->errorInfo[0]`.

**Как заметил:** при чтении исходников `PDOException` и документации
Laravel `QueryException`.

**Исправление:** `$sqlstate = $e->errorInfo[0] ?? null;`.

### Кейс 5. `23514` (CHECK violation) → `409` вместо `422`

**Что предложил ИИ:** «Любое нарушение констрейнта → `409 Conflict`».

**Почему неверно:** `409` — семантически «конкурентный конфликт». `23514`
(CHECK violation) — это **невалидные данные** (инвертированный интервал,
обход FormRequest), а не конфликт. Правильно — `422` с логом уровня `error`,
потому что это баг валидации, а не race condition.

**Как заметил:** при проектировании `CreateBookingAction` и сопоставлении
SQLSTATE с семантикой HTTP.

**Исправление:** `23P01` → `409` (race через EXCLUDE), `23514` → `422` +
`Log::error`.

### Кейс 6. Route model binding в `destroy` — выход за пределы задачи

**Что предложил ИИ.** Переписать `destroy(int $id)` на `destroy(Booking $booking)`
с route model binding — «для консистентности с `today(Room $room)` и
идиоматичности Laravel».

**Почему неверно.**
- Роут объявлен как `Route::delete('/bookings/{id}', ...)` — параметр `{id}`.
  Для route model binding нужно переименовать его в `{booking}`, то есть
  **изменить чужой код** (`routes/api.php`), который мы не проектировали.
- Мы уже зафиксировали правило: «меняем чужой код только если ТЗ прямо
  требует или это уязвимость/баг». Переименование параметра роута не
  подходит ни под один критерий — это чисто стилистическая правка.
- ТЗ прямо говорит: «`index` и `today` исправлять не нужно» — сигнал, что
  чужой код в контроллере вообще не трогаем без явной необходимости.

**Как заметил.**
- Перед применением проверил `routes/api.php` через `grep "bookings"` —
  увидел `{id}`, а не `{booking}`. До правки это дало бы 404/500 на
  `destroy`: Laravel попытался бы разрешить `$booking` из пустого
  параметра.
- Остановили правку **до** коммита. Изначальная рекомендация ИИ была
  ошибочной и нарушала наше же правило.

**Решение.** Оставили `destroy(int $id)` + `Booking::findOrFail($id)` без
изменений. Это корректный Laravel-код, просто менее лаконичный. На звонке:
*«оставил как есть — переименовывать параметр в чужом роуте ради стиля
не стал. Route model binding был бы идиоматичнее, но это правка вне
объёма задачи».*

**Урок.** «Идиоматичнее / чище / консистентнее» — не повод трогать чужой
код. Особенно когда ТЗ явно очерчивает границы («`index` и `today` не
исправлять»). Правило «меняем только то, что требует ТЗ» должно
применяться и к рекомендациям ИИ — включая рекомендации самого ассистента.

### Кейс 7. Ревью рекомендовало сузить тип `\Throwable` до `RuntimeException`

**Что предложил ИИ.** «Метод `translateDatabaseFailure` возвращает `\Throwable`,
что размывает намерение. Указать более конкретный тип, например
`RuntimeException` — так как `BookingConflictException` и `ValidationException`
наследуются от него».

**Почему неверно.**
- `Illuminate\Validation\ValidationException` наследуется от `Exception`,
  **не** от `RuntimeException`. В Laravel это факт:
  `class ValidationException extends Exception implements ValidationException`.
- Если изменить возвращаемый тип на `RuntimeException`, то
  `ValidationException::withMessages(...)` из метода не скомпилируется —
  она не подходит под этот тип.
- `\Throwable` — минимально общий корректный тип: `BookingConflictException`
  (extends `RuntimeException`), `ValidationException` (extends `Exception`),
  `QueryException` (extends `PDOException`) — все реализуют `Throwable`.
  `RuntimeException` — потомок `Exception`, но не общий предок всех трёх.

**Как заметил.** Проверил иерархию наследования `ValidationException`
в исходниках Laravel и документации. `RuntimeException` и `ValidationException`
находятся в разных ветках дерева: `RuntimeException` extends `Exception`,
`ValidationException` тоже extends `Exception`, но `RuntimeException`
не является общим предком.

**Решение.** Оставили `Throwable` (Pint применил `use Throwable;` и убрал
leading backslash — правило `fully_qualified_strict_types`). На звонке:
*«`Throwable` — минимальный тип, покрывающий три разных исключения из метода.
`RuntimeException` не подходит, потому что `ValidationException` от него
не наследуется. Сужение типа сломало бы компиляцию».*

**Урок.** «Более конкретный тип» — не всегда лучше. Если метод возвращает
разные ветки иерархии исключений, общий интерфейс (`Throwable`) — единственный
корректный выбор. Сужать до конкретного класса можно, только если
**все** возвращаемые исключения — его потомки. Это проверяется по исходникам,
а не по интуиции.

## 3. Что проверил вручную (и не доверил ИИ)

**Факты по репозиторию (через GitHub API, не «на веру»):**
- FK на `room_id` и `user_id` в миграции `bookings` **есть** — проверил
  через `raw.githubusercontent.com`, не поверил утверждению «нет FK».
- Канал `bookings` в `config/logging.php` **определён** — проверил.
- Маршруты **защищены** `auth:sanctum` — проверил в `routes/api.php` и через
  тест `BookingIndexTest::test_requires_authentication` (ожидает 401).

**Баги (через `curl` на локальном окружении):**
- SQL-инъекция: запрос на свободную комнату 2 с `' OR '1'='1` → 409.
- Mass assignment: `user_id: 2` с токеном Анны → бронь от Бориса.
- 500 без `user_id`: `SQLSTATE[23502]`.
- Пересечение «впритык»: `10:00–11:00` + `11:00–12:00` → 409.
- IDOR: Борис удаляет бронь Анны → 204.
- TZ: московская комната + `10:00+07:00` → 201 (должно быть 422).

**Семантику, которую ИИ мог перепутать:**
- `tstzrange('2026-01-02', '2026-01-01')` — **empty range**, не пересекается
  ни с чем. Поэтому нужен `CHECK (ends_at > starts_at)` — иначе `EXCLUDE`
  пропустит инвертированный интервал.
- `EXCLUDE` с `room_id WITH =` требует `btree_gist` для integer.
- `$e->errorInfo[0]` надёжнее `$e->getCode()` для SQLSTATE.

**Порядок работ (не доверил ИИ «как удобнее»):**
- Миграция → FormRequest → Action → Controller → Policy → Resource → тесты.
- Обоснование: миграция — самое рискованное (права на `CREATE EXTENSION`);
  Action принимает уже валидированные данные; Controller тонкий.
